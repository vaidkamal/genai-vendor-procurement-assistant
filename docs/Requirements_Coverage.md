# Requirements coverage — Topic 4, Vendor Comparison and Procurement Assistant

Each line of the capstone brief, and where the evidence sits in this folder.

## Minimum requirement

| Brief | Evidence |
|---|---|
| Select one purchasing category | Business laptops for new-hire onboarding — `data/requirement_intake.json` |
| Create three fictional vendor quotations | `data/quotations/Q1…Q3*.pdf` (generated by `src/00_generate_sample_quotations.py`; three layouts, USD and EUR, itemised vs. bundled) |
| Standardise the information | `src/01_parse_quotations.py` → `outputs/standardised_quotations.csv` / `.json` (FX, shipping, warranty extension, business→calendar days) — screenshot 02 |
| Compare vendors using criteria chosen by the learners | Six weighted criteria with printed formulas — `src/02_compare_vendors.py`, `outputs/comparison_report.md`, README "Decision criteria" (with the reasoning for each weight) — screenshots 01, 05 |
| Produce a recommendation | `outputs/comparison_results.json` → recommendation block; `outputs/ai_recommendation_summary.md` (Claude-written explanation) — screenshot 04 |
| Give a procurement user the ability to review or change the decision | `app/dashboard.html`: weight sliders, approve / award to different vendor / request clarification / reject, mandatory justification — screenshots 05, 06 |

## What the final demonstration should show

| Brief | How it is shown |
|---|---|
| Inconsistent vendor information becomes a clear comparison | Open the three PDFs side by side, then `outputs/standardised_quotations.csv` and the dashboard comparison table (screenshot 02) |
| …and a reviewable recommendation | Ranking panel with "Recommended" badge and policy status; officer can move sliders and watch the ranking change (screenshot 05) |
| Learners explain the selected decision criteria | README "Decision criteria" table with the reasoning per weight; "How scores are calculated" in `comparison_report.md`; slider help text in the dashboard |
| System does not make purchases or financial commitments independently | Red guardrail banner (screenshot 08); policy P-07/P-09; no e-mail/ERP/payment code in `src/` (`grep -r "smtplib\|requests.post" src/` → nothing); e-mails are drafts; voice agent states three times it cannot accept, order or pay; "Record decision" only writes an instruction for Finance — see `docs/Demo_Script.md` step 7 |

## Common expectations for every capstone

| Expectation | Evidence |
|---|---|
| One clear business problem | Three quotes → one approved vendor; no unrelated features |
| Manageable synthetic data | 3 PDFs, 1 intake file, 1 policy file, 1 performance file — all fictional |
| At least one working journey from input to useful output | `python src/run_pipeline.py` runs PDFs → dashboard end-to-end |
| Where generative AI adds value vs. deterministic logic | README table and slide 2 of the Project Overview |
| Human review point for important decisions and external communication | Officer decision panel; e-mails and call outcomes go through the officer |
| One or two business metrics | Analyst time per three-quote comparison; % of policy exceptions caught before PO |
| Limitations, risks, deployment prerequisites | README "Limitations, risks and what real deployment would need" |
